==============================================================================
AXION — HOW TO START THE PROJECT
==============================================================================

Axion is two services plus a database:

    db   PostgreSQL 16      (Docker only; local runs can use SQLite instead)
    api  FastAPI + uvicorn  http://localhost:8000
    web  Next.js            http://localhost:3000   <- open this one

The browser only ever talks to the web service on :3000. Next.js proxies every
/api/* request to the API on :8000, so the session cookie stays same-origin.
You never need to open :8000 by hand — except to read the API docs.


------------------------------------------------------------------------------
OPTION A — DOCKER COMPOSE (the one command)
------------------------------------------------------------------------------

Requirements: Docker Desktop (or Docker Engine + the Compose plugin) running.

    cp .env.example .env        # optional — every value has a working default
    docker compose up --build

Then open:  http://localhost:3000

That is the whole startup. The API container's entrypoint
(api/scripts/entrypoint.sh) does three things on boot, in order:

    1. alembic upgrade head      create/patch the Postgres schema
    2. python -m app.seed        only when SEED_DEMO=true (the default)
    3. uvicorn app.main:app      serve the API

The seed prints a table to the container logs showing the naive average next to
the Axion Z-score leaderboard. The two disagree on purpose:

    Flashy Demo   raw 6.40  ->  Axion 46.66  (rank -2)
    Quiet Craft   raw 6.00  ->  Axion 48.79  (rank +2)

Useful follow-ups:

    make logs        follow the container logs
    make down        stop everything (keeps the database volume)
    make reset       stop and DELETE the database volume (clean cold start)
    make seed        re-run the seed inside the running API container


------------------------------------------------------------------------------
OPTION B — RUN IT LOCALLY (no Docker)
------------------------------------------------------------------------------

Requirements: Python 3.12+ and Node 18+ (verified on Python 3.12.10, Node 24).
Commands below are Git Bash on Windows; macOS/Linux notes are inline.

STEP 1 — API dependencies (first time only)

    cd api
    python -m venv .venv

    # Windows (Git Bash):
    ./.venv/Scripts/python.exe -m pip install -r requirements.txt

    # macOS / Linux:
    # .venv/bin/python -m pip install -r requirements.txt

STEP 2 — Create the database, load the demo data, and start the API

    cd api

    export DATABASE_URL="sqlite+pysqlite:///./axion-dev.db"
    export MOCK_GITHUB=true
    export SEED_DEMO=true
    export EVENT_NAME="Axion Demo Hackathon"
    export EVENT_START="2026-09-23T19:15:00+00:00"
    export EVENT_END="2026-09-28T19:15:01+00:00"

    # 1. creates the tables AND the demo dataset (safe to re-run; it skips if
    #    the database is already populated)
    ./.venv/Scripts/python.exe -m app.seed

    # 2. start the API
    ./.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

    # macOS / Linux: swap ./.venv/Scripts/python.exe for ./.venv/bin/python

Leave that terminal running. The local SQLite file is written to
api/axion-dev.db, which is git-ignored.

STEP 3 — The web app (second terminal)

    cd web
    npm install          # first time only
    npm run dev          # serves http://localhost:3000

STEP 4 — Open the app

    http://localhost:3000

Check both are alive:

    curl http://127.0.0.1:8000/api/health
    curl http://127.0.0.1:3000/api/health      # same answer, through the proxy


------------------------------------------------------------------------------
THE SUBMISSION WINDOW
------------------------------------------------------------------------------

EVENT_START and EVENT_END are read from the environment at API boot, and the
deadline is enforced against the server clock, never the browser's.

Leave both blank and you get a 72-hour event that is OPEN NOW — drafting,
editing and submitting work out of the box. (A blank EVENT_END used to resolve to
"ended at boot", which closed submissions the moment the API started; that was a
real bug in the one-command path, and it is fixed.)

Set them explicitly to demo a specific window:

    EVENT_START=2026-09-23T19:15:00+00:00     # in the past
    EVENT_END=2026-09-28T19:15:01+00:00       # in the future

An explicit value always wins, so a closed event stays closed. /api/health
reports the window that was actually resolved, including whether it is closed.

To run the imported dataset instead — 40 projects, 12 judges, incomplete review
batches, duplicates, and an event that has already closed:

    SEED_DEMO=true SEED_MODE=fixtures EVENT_SOURCE=fixtures

EVENT_SOURCE=fixtures takes the window from fixtures.json, so the imported
deadline is genuinely enforced rather than described.

That is also a single flag:

    DOGFOOD_FIXTURE_MODE=true

it implies both variables above and enables the same offline sign-in / checker
credential gate, and an explicit SEED_MODE or EVENT_SOURCE still wins. The
checker headers .dogfood.toml reads are served either way.

SIGNING IN — INCLUDING WITH THE NETWORK OFF
------------------------------------------------------------------------------

GitHub OAuth is optional and off by default (no credentials set). With
MOCK_GITHUB=true or SEED_DEMO=true the sign-in page also shows a "Local Dev
Login" panel with one-click buttons that make zero external calls.

    Role        Email                    Password
    ----------  -----------------------  -------------
    Organiser   admin@axion.dev          axion-admin
    Organiser   admin@axion.local        password       (offline account)
    Judge       disciplined@axion.dev    axion-judge
    Judge       expansive@axion.dev      axion-judge
    Judge       balanced-a@axion.dev     axion-judge
    Participant hacker@axion.local       password       (offline, on a team)
    Participant hacker01@axion.dev ...   axion-hacker

The one-click buttons are: "Login as Admin", "Login as Judge", "Login as
Hacker". The endpoint behind them returns 403 unless the deployment is in demo
mode, so it cannot become a backdoor in a live event.

------------------------------------------------------------------------------
RUN THE ACCEPTANCE CHECKS
------------------------------------------------------------------------------

There are two, and they write to different files so neither overwrites the other.

1. The manifest-driven self-check — the artefact the challenge asks for. It reads
   .dogfood.toml (routes, roles, status codes, dataset expectations), fetches its
   header credentials from the API, and never mutates a running event:

    # fixture dataset booted on :8000 (see the window section above)
    AXION_API_URL=http://127.0.0.1:8000 \
      api/.venv/Scripts/python.exe api/scripts/dogfood_check.py .dogfood.toml \
      --out acceptance-report.txt

2. The tier-by-tier suite (T0–T4 plus the bonus claims), which prints a SKIP with
   its reason wherever something cannot be observed:

    AXION_API_URL=http://127.0.0.1:8000 \
      api/.venv/Scripts/python.exe api/scripts/acceptance.py \
      --out acceptance-report.axion.txt

With make installed the same two runs are:

    make acceptance          # the manifest self-check
    make acceptance-axion    # the tier suite

Exit code 0 means nothing failed. Neither report is a run of an
organiser-provided suite: no organiser .dogfood.toml, run.py or fixtures.json
existed in this repository, in the brief, or anywhere on the build machine, and
both reports say so in their first lines.

Where the checker's credentials come from (dev deployments only):

    GET /api/dev/checker-headers
      -> organizer / judge_a / judge_b / participant as Authorization: Bearer …

The API also prints those four headers once at boot. Nothing is embedded in
.dogfood.toml, so the manifest stays valid on any machine.

The fixture file itself can be validated with no server at all:

    api/.venv/Scripts/python.exe api/scripts/validate_fixtures.py

Exit 0 means structurally valid, 1 names the invalid records, 2 means the file
could not be read. The rules are the ones the importer enforces before it writes
anything, and the report contains no clock and no database state.

The unit tests are separate and need no running server (run from api/ so the
`app` package is importable), and they include the two-clean-import determinism
check:

    cd api && ./.venv/Scripts/python.exe -m pytest -q
    cd web && npm run typecheck
    cd web && npm run build


------------------------------------------------------------------------------
TROUBLESHOOTING
------------------------------------------------------------------------------

"no such table: submissions" / Internal Server Error on every data page
    The database has no schema. This happens when the API is started with bare
    uvicorn, which skips the migrate+seed step that the Docker entrypoint runs.
    Fix: run the seed once against the same DATABASE_URL, then restart:

        ./.venv/Scripts/python.exe -m app.seed

Empty leaderboard or "0 projects entered"
    Same cause as above, or SEED_DEMO was not true at boot.

Submissions or drafts rejected as late
    EVENT_END is genuinely in the past — either you set it, or EVENT_SOURCE=fixtures
    loaded the fixture window, which closed on 2026-08-04. /api/health shows the
    resolved window and `closed`. See the window section above.

Page loads but a data panel is empty
    The web service cannot reach the API. Confirm http://127.0.0.1:8000/api/health
    answers, then hard-reload.

/api/* returns 404 or the wrong host
    Next.js bakes rewrite destinations in at BUILD time
    (see web/next.config.mjs and API_INTERNAL_URL). Restart `npm run dev`, or
    rebuild the web image, after changing that value.

Port 3000 or 8000 already in use
    Find and stop the listener, or run on another port:

        netstat -ano | grep LISTENING | grep ":8000"
        taskkill //PID <pid> //F

        npm run dev -- -p 3100
        uvicorn app.main:app --port 8001
